## 2. The blocker, stated precisely

`#[Entry(kind: EntryKind.Web)] function web(Http.ServeConfig cfg, AppSettings app): void` — spec §1
verbatim — fails today, and it fails **twice**:

1. Before config desugar, its shape is neither Cli nor Web, so `entry_role` is `None`.
2. `desugar_config` therefore *does* rewrite it (injecting the providers) — leaving `(): void`,
   whose `entry_role` is `Cli`. The declared kind is `Web`. `entry_role(f) != Some(role)` →
   **`E-ENTRY-SIG`**.

So the fix is not "teach `entry_role` about config params". It is that **after S3.1 retired DEC-191
inference, a structural validator for the `Web` role no longer has a job to do** — the kind is
declared. The agreement check should validate the *post-desugar* shape against the declared kind,
and a `Web` entry's post-desugar shape is `(): void` — identical to `Cli`'s. That is fine: the check
exists to catch `#[Entry(kind: Web)] function f(int x): string`, not to distinguish Cli from Web.

## 3. The architecture — how a closure handler reaches N non-`Send` workers

This is the piece that must not be re-derived. The current runtime calls a **fixed named entry** per
request. Under §1 the handler is a **closure value** created inside the Web entry, and closure values
are `Rc`-bearing: they cannot cross a thread boundary to reach the worker pool.

**Resolution — invert the loop, do not move the closure.** Each worker already builds its own program
instance via `HandlerFactory`. So:

1. **Parent, once:** resolve the `Http.ServeConfig` by evaluating its `#[Config]` provider (DEC-318
   machinery, already shipped; providers are pure functions). This yields `host`/`port`/`workers`/
   `timeout`/`maxBodySize` *before* any worker exists — which is required, since `workers` is itself
   a config field.
2. **Parent, once:** bind the `TcpListener` at `host:port`. Share it as `Arc<TcpListener>` — `accept()`
   is thread-safe, so N workers accepting on one listener needs no `SO_REUSEPORT`.
3. **Per worker:** run the **Web entry function itself** on that thread. It constructs its own closure
   on its own `Rc` heap and calls `Http.serve(cfg, handler)`.
4. **`Http.serve` native:** picks up the shared listener from a process-global (the `DOCROOT`
   `OnceLock` pattern already in `src/serve/mod.rs:46`), then runs the accept loop **on the calling
   thread**, invoking the closure per request through the existing re-entrant-call machinery
   (banked technique: `higher-order-natives-reentrant-vm`).

Nothing `Rc`-bearing ever crosses a thread. The `Send + Sync` boundary stays exactly where it is
today (the checked `Program` + the reified table). `--workers 1` remains the single-threaded path.

**Consequence to state in the slice, not discover later:** `Http.serve` never returns, so any code
after it in the Web entry is unreachable — the totality checker already knows qualified never-calls
(the `Debug.dd`/`Runtime.exit` precedent), so `Http.serve` joins that set and code after it is
`W-UNREACHABLE`.

## 4b. S3.3b — SHIPPED 2026-08-22

`ast::entry_shape_matches(f, declared)` replaces `entry_role(f) == Some(role)` as the checker's
`E-ENTRY-SIG` gate (`src/checker/program/entry_points.rs`). The two had silently become different
questions: `entry_role` asks *"what role would this shape imply?"* — the right question only while
DEC-191 inferred the role. S3.1 retired inference, so the question is now *"is this shape legal FOR
the declared role?"*, and one shape can be legal for two roles.

**Two existing tests changed, both deliberately, neither by weakening an assertion:**

- `entry_diagnostics_quote_the_qualified_form_not_bare` — its FIXTURE happened to be `Web` +
  `(): void`, the shape S3.3b legalizes, so it stopped producing the `E-ENTRY-SIG` whose *wording*
  is its actual subject. Fixture repointed to a still-invalid shape; assertion untouched.
- `web_kind_on_cli_signature_is_sig_error` → `web_kind_on_a_cli_only_signature_is_sig_error` — this
  one asserted the rule D5 retires. Rewritten to pin what survives: `(): int` (a process exit code)
  and `(List<string>)` (argv) are Cli shapes a `Web` entry must still reject. Net coverage went UP.

**Sabotage-verified**, not merely green: forcing the `Web` arm to accept everything turned 3 tests
red including both controls; restore confirmed byte-identical.

**`phg explain E-ENTRY-SIG` updated in the same change** (Invariant 17) — it still described a Web
entry as only `(Request): Response`.

**Intermediate state, stated rather than discovered later:** a `(): void` Web entry now *checks*
but cannot yet *serve* — `phg serve` still resolves the `respond` entry and will report it missing.
That is S3.3a's job. No previously-working program changes behaviour: the shape being legalized did
not compile at all before.

## 5. ✅ Q1 — RULED 2026-08-22: `handle` retires with `respond`

D5 retires `respond(bytes): bytes` and says "typed `(Request): Response` is THE web handler" — but in
§1 that signature is the **closure passed to `Http.serve`**, not the entry. Today `handle` *is* the
entry, and every shipped `examples/web/*` uses it, so the spec's silence was a real fork.

**Ruled by the developer: retire `handle` too.** See the Decisions Log entry above for the rationale
and the full migration surface. S3.3c is therefore unblocked, and its scope grew: delete
`HTTP_RESPOND_BRIDGE`, the `respond_bridge` field and its ~30 `None` initializers in
`src/cli/preludes.rs`, plus `SERVE_ENTRY` and the by-name entry resolution in `src/serve/handlers.rs`.

**What this makes newly load-bearing in S3.3a:** with no named-entry fallback at all, `Http.serve`
becomes the ONLY way a program can serve — so its startup error (a `Web` entry that never calls
`Http.serve`) has to be a good one, not an afterthought. Give it a code and an `explain` entry in
the same change.
