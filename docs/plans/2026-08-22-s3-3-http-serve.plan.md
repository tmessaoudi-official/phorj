## 2. The blocker, stated precisely

`#[Entry(kind: EntryKind.Web)] function web(Http.ServeConfig cfg, AppSettings app): void` — spec §1
verbatim — fails today, and it fails **twice**:

1. Before config desugar, its shape is neither Cli nor Web, so `entry_role` is `None`.
2. `desugar_config` therefore *does* rewrite it (injecting the providers) — leaving `(): void`,
   whose `entry_role` is `Cli`. The declared kind is `Web`. `entry_role(f) != Some(role)` →
   **`E-ENTRY-SIG`**.

So the fix is not "teach `entry_role` about config params". It is that **after S3.1 retired DEC-191
inference, a structural validator for the `Web` role no longer has a job to do** — the kind is
declared. The agreement check should validate the *post-desugar* shape against the declared kind,
and a `Web` entry's post-desugar shape is `(): void` — identical to `Cli`'s. That is fine: the check
exists to catch `#[Entry(kind: Web)] function f(int x): string`, not to distinguish Cli from Web.

## 3. ⚠ SUPERSEDED 2026-08-22 — see §3b. The inverted-loop design below does NOT survive contact.

**Two facts kill it, both found by reading the code rather than reasoning about it:**

1. **A native cannot call a method.** The closure returns a `Response`, the loop needs bytes, and
   turning one into the other is `.serialize()` — a METHOD. `ClosureInvoker` invokes closures, not
   methods, so the native has no way to do it. The existing `HTTP_RESPOND_BRIDGE` already solves this
   exact shape by keeping HTTP policy in phorj (`handle(req).serialize()`), and that is also what
   keeps the 400-on-malformed behaviour byte-identical across backends.
2. **The invoker does not outlive the native call.** `NativeEval::HigherOrder` is handed a
   `&mut ClosureInvoker` supplied by the backend *for the duration of that one dispatch*. A native
   that ran an accept loop would have to hold it for the process lifetime.

Kept, not deleted: a fresh session must not rebuild this.

## 3b. The architecture — registration, not loop-in-native

**`Http.serve(cfg, handler)` REGISTERS and RETURNS. The loop stays exactly where it is.** The `Web`
entry is a *closure factory*, nothing more — so there is no probe/serve mode split, and the
transport, keep-alive, static-file interception and the `(Value, String)` stdout contract are all
untouched. `src/serve/mod.rs`'s own doc sentence — the runtime "only shuttles raw bytes to a single
Phorj entry" — stays true; only how that entry is obtained changes.

| Piece | Design |
|---|---|
| Prelude `Http.serve(ServeConfig cfg, (Request) => Response handler): void` | wraps the typed handler into a `(bytes) => bytes` closure (`Request.parse` → `handler(req).serialize()`, malformed → 400) and passes it to the native. HTTP policy stays in phorj — same reason the legacy bridge does. `Type::Function`/`Ty::Function` already exist (`(A) => B`, as `db.transaction` uses), so no checker-surface work |
| Native `Core.Native.Http.registerServe(cfg, rawHandler)` | `NativeEval::Pure` — it never *invokes* the closure, so it needs no invoker. Stores the handler in a **thread-local** (a closure `Value` is `Rc`-bearing and must NEVER enter a process global) and the config in a **process-global `Mutex<Option<ServeCfg>>`** of plain Rust scalars (`Send`). Two slots, deliberately different kinds |
| Factory | per worker: run the `Web` entry once on that thread → the native fills the thread-local → take the closure → return a `Handler` that calls it per request. Still a `HandlerFactory`, so `tests/serve.rs`'s in-memory `Transport` works unchanged and no listener seam is needed |
| Per-request call | interpreter `call_closure` / VM `call_closure_value` (currently `pub(super)`, trivially exposable) |

**Semantics to pin deliberately, not discover:** the closure's CAPTURES persist across requests (§1's
example captures `app`, so this is ruled territory), while program statics re-seed per request as
they do today. The legacy `respond` path keeps its exact current behaviour until S3.3c.

**Flag-vs-config conflict — refuse, do not pick.** D1 already ruled the ordering (CLI flag > env >
`#[Config]` > `phorj.json` > attr default); what is pending in Part C is the *machinery*. So
cfg-silently-wins contradicts a ruled ordering, and flag-silently-wins makes `cfg.workers` inside the
program disagree with the running pool. Increment 2 hard-errors when the new path is taken AND
explicit serve flags were passed, naming the pending ruling. An error relaxes later without breaking;
silent behaviour does not. Legacy path keeps flags unchanged.

## 3c. (historical) the inverted-loop design — SUPERSEDED, see §3 and §3b

This is the piece that must not be re-derived. The current runtime calls a **fixed named entry** per
request. Under §1 the handler is a **closure value** created inside the Web entry, and closure values
are `Rc`-bearing: they cannot cross a thread boundary to reach the worker pool.

**Resolution — invert the loop, do not move the closure.** Each worker already builds its own program
instance via `HandlerFactory`. So:

1. **Parent, once:** resolve the `Http.ServeConfig` by evaluating its `#[Config]` provider (DEC-318
   machinery, already shipped; providers are pure functions). This yields `host`/`port`/`workers`/
   `timeout`/`maxBodySize` *before* any worker exists — which is required, since `workers` is itself
   a config field.
2. **Parent, once:** bind the `TcpListener` at `host:port`. Share it as `Arc<TcpListener>` — `accept()`
   is thread-safe, so N workers accepting on one listener needs no `SO_REUSEPORT`.
3. **Per worker:** run the **Web entry function itself** on that thread. It constructs its own closure
   on its own `Rc` heap and calls `Http.serve(cfg, handler)`.
4. **`Http.serve` native:** picks up the shared listener from a process-global (the `DOCROOT`
   `OnceLock` pattern already in `src/serve/mod.rs:46`), then runs the accept loop **on the calling
   thread**, invoking the closure per request through the existing re-entrant-call machinery
   (banked technique: `higher-order-natives-reentrant-vm`).

Nothing `Rc`-bearing ever crosses a thread. The `Send + Sync` boundary stays exactly where it is
today (the checked `Program` + the reified table). `--workers 1` remains the single-threaded path.

**Consequence to state in the slice, not discover later:** `Http.serve` never returns, so any code
after it in the Web entry is unreachable — the totality checker already knows qualified never-calls
(the `Debug.dd`/`Runtime.exit` precedent), so `Http.serve` joins that set and code after it is
`W-UNREACHABLE`.

## 4b. S3.3b — SHIPPED 2026-08-22

`ast::entry_shape_matches(f, declared)` replaces `entry_role(f) == Some(role)` as the checker's
`E-ENTRY-SIG` gate (`src/checker/program/entry_points.rs`). The two had silently become different
questions: `entry_role` asks *"what role would this shape imply?"* — the right question only while
DEC-191 inferred the role. S3.1 retired inference, so the question is now *"is this shape legal FOR
the declared role?"*, and one shape can be legal for two roles.

**Two existing tests changed, both deliberately, neither by weakening an assertion:**

- `entry_diagnostics_quote_the_qualified_form_not_bare` — its FIXTURE happened to be `Web` +
  `(): void`, the shape S3.3b legalizes, so it stopped producing the `E-ENTRY-SIG` whose *wording*
  is its actual subject. Fixture repointed to a still-invalid shape; assertion untouched.
- `web_kind_on_cli_signature_is_sig_error` → `web_kind_on_a_cli_only_signature_is_sig_error` — this
  one asserted the rule D5 retires. Rewritten to pin what survives: `(): int` (a process exit code)
  and `(List<string>)` (argv) are Cli shapes a `Web` entry must still reject. Net coverage went UP.

**Sabotage-verified**, not merely green: forcing the `Web` arm to accept everything turned 3 tests
red including both controls; restore confirmed byte-identical.

**`phg explain E-ENTRY-SIG` updated in the same change** (Invariant 17) — it still described a Web
entry as only `(Request): Response`.

**Intermediate state, stated rather than discovered later:** a `(): void` Web entry now *checks*
but cannot yet *serve* — `phg serve` still resolves the `respond` entry and will report it missing.
That is S3.3a's job. No previously-working program changes behaviour: the shape being legalized did
not compile at all before.

## 5. ✅ Q1 — RULED 2026-08-22: `handle` retires with `respond`

D5 retires `respond(bytes): bytes` and says "typed `(Request): Response` is THE web handler" — but in
§1 that signature is the **closure passed to `Http.serve`**, not the entry. Today `handle` *is* the
entry, and every shipped `examples/web/*` uses it, so the spec's silence was a real fork.

**Ruled by the developer: retire `handle` too.** See the Decisions Log entry above for the rationale
and the full migration surface. S3.3c is therefore unblocked, and its scope grew: delete
`HTTP_RESPOND_BRIDGE`, the `respond_bridge` field and its ~30 `None` initializers in
`src/cli/preludes.rs`, plus `SERVE_ENTRY` and the by-name entry resolution in `src/serve/handlers.rs`.

**What this makes newly load-bearing in S3.3a:** with no named-entry fallback at all, `Http.serve`
becomes the ONLY way a program can serve — so its startup error (a `Web` entry that never calls
`Http.serve`) has to be a good one, not an afterthought. Give it a code and an `explain` entry in
the same change.

## 4c. S3.3c — SHIPPED 2026-08-22

`respond` is gone. `Http.serve(cfg, handler)` is the only way a program registers a handler, on both
backends.

**One defect this slice had to fix that §5 did not anticipate.** §5 said the startup error "has to be
a good one, not an afterthought" — it was not enough. With the by-name fallback deleted, a legacy
program's `(Request): Response` entry is STILL resolved (S3.3b deliberately kept that shape legal for
`kind: Web`), and the factory called it with no arguments. The startup message for every pre-D5 serve
program was therefore `` `handle` expects 1 argument(s), got 0 `` — an opaque arity complaint, on the
one diagnostic every migrating user is guaranteed to read exactly once. `web_entry_name` now refuses a
parameterised web entry BEFORE calling it, on ARITY rather than parameter type.

**`E-SERVE-NO-HANDLER`** covers both unservable shapes under one code — they are the same condition
from the user's side ("nothing will answer a request") and differ only in the fix. Extracted as a
NAMED const so `doc-guards.sh` and `surface-ratchet.sh` can both see it.

**The checker was deliberately NOT narrowed.** Rejecting `(Request): Response` for `kind: Web` is
S3.3d's, with the example migration: doing it here fails `phg check` on the five shipped
`examples/web/*` in the same commit that removed their bridge, taking the example byte-identity glob
red for a reason unrelated to what it gates.

**Test-surface changes, stated because two look like weakenings and are not:**

- `core_http_handle_is_servable_via_injected_respond_bridge` DELETED — it tested the bridge. The
  Core.Http serve path it covered is asserted on both backends by `http_serve_closure_handler_is_servable`
  (S3.3a), *including* the malformed → 400 case that test never checked. Coverage rose.
- `respond_non_bytes_return_degrades_to_500` → `a_non_bytes_handler_return_degrades_to_500`, driven by
  a SYNTHETIC `Handler` instead of phorj source. The old fixture is now unrepresentable — the checker
  rejects a non-`bytes` return long before the runtime sees it — but the branch stays, because the
  `Handler` TYPE still admits any `Value` and an untested defensive branch is how a panic ships.
- `a_void_web_entry_does_not_get_the_legacy_respond_bridge` → `importing_core_http_synthesizes_no_respond_entry_for_any_web_shape`:
  the assertion INVERTED (its control asserted the bridge still fired for the legacy shape) and now
  covers both shapes.
- `SERVE_PROGRAM` no longer hand-rolls `Request`/`Response` + parse/serialize in pure Phorj: `Http.serve`
  takes CORE.HTTP's types, so a program declaring its own classes of those names cannot hand it a
  handler. That demonstration is what `examples/web/server.phg` exists for, and it stays
  byte-identity-gated; here it was incidental to tests that assert the LOOP.

**Not in this slice, and blocked rather than skipped:** the registered `ServeConfig` is still stored
and unread — `phg serve` binds host/port from CLI flags. Making the config win requires the
flag-vs-config conflict to hard-error rather than silently pick a winner, which is the pending S3.2
Part C precedence ruling (§6). Wiring it now would mean inventing a precedence rule the developer has
not made.
